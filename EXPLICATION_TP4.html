Le but : savoir QUAND l'AutoML se justifie

L'AutoML met en concurrence des familles de modeles et regle leurs hyperparametres dans un budget de temps. Le TP ne cherche pas un vainqueur, mais ce que l'automatisation fait - et ne fait pas - a ta place.

Le code, fichier par fichier

Ouvre le projet dans VS Code : chaque script commence par le meme resume (ROLE / ENTREE / SORTIE / A RETENIR). Lis-les dans cet ordre, c'est l'ordre d'execution.

reports/flaml_*.log   -> le journal de chaque recherche (1 ligne = 1 essai)
reports/comparatif.md -> le tableau local vs cloud

1. donnees.py

Role : Fabrique le jeu de 5000 transactions bancaires (synthetiques) avec une graine fixe.

Entree : rien (tirage aleatoire avec la graine 7)

Sortie : data/transactions.csv (5000 lignes, 568 fraudes)

A retenir : Meme graine = memes donnees pour toute la promo : c'est la base de la reproductibilite.

2. src/references.py

Role : Calcule les 2 points de comparaison : regression logistique (simple) et foret 500/16 (reglage manuel du TP2).

Entree : data/transactions.csv

Sortie : 2 runs MLflow dans tp4-automl (F1 0.7407 et 0.8669)

A retenir : Sans reference, un score d'AutoML ne veut rien dire.

3. src/automl.py

Role : Lance FLAML pendant un budget de temps donne : il essaie plusieurs familles de modeles et garde la meilleure.

Entree : data/transactions.csv + budget en secondes (argument)

Sortie : reports/flaml_XXs.log (tous les essais) + un run MLflow flaml-XXs

A retenir : metric='f1' = ce qu'on optimise ; le jeu de test ne sert qu'a la fin pour juger le gagnant.

4. src/rendement.py

Role : Relit les runs dans MLflow et trace le F1 en fonction du budget, avec les references en pointilles.

Entree : les runs de l'experience tp4-automl

Sortie : reports/rendement.png

A retenir : Rendement decroissant : 120 s n'a rien apporte de plus que 60 s.

5. src/inspecter.py

Role : Lit le journal de FLAML pour savoir ce qu'il a VRAIMENT essaye (familles, nombre d'essais, meilleur score).

Entree : reports/flaml_60s.log

Sortie : affichage : essais par famille + essai gagnant

A retenir : Un modele AutoML n'est acceptable que si on peut expliquer ce qui a ete essaye.

6. src/fuite.py

Role : Demontre une fuite de donnees : on ajoute une colonne qui contient la reponse (numero de litige).

Entree : data/transactions.csv + colonne piegee

Sortie : affichage : F1 = 1.0 en test puis 0.0 'en production'

A retenir : Un score parfait = presque toujours une fuite. L'AutoML ne la detecte pas.

Ce qu'il faut retenir

  • Toujours une baseline (logistique 0.74) : un score AutoML seul ne veut rien dire.
  • AutoML = baseline forte en minutes, pas forcement le meilleur modele (0.858 vs 0.867 manuel). Ecart de 0.01 sur 134 fraudes = non significatif.
  • Exiger le journal des essais : un modele AutoML n'est acceptable que si on peut dire ce qui a ete essaye.
  • Un score parfait sur un probleme difficile = presque toujours une fuite. Verifier pour chaque colonne : existe-t-elle au moment de la decision ?
  • Restent a ta charge : definir le probleme et la metrique, la qualite des donnees, la validation metier, le deploiement, le monitoring.
  • Local vs manage : local = gratuit, reversible, donnees chez soi ; cloud = infra et deploiement integres, mais facture a l'heure et verrouillage fournisseur.

Pieges

Le budget est un tempsLes resultats dependent de la vitesse de la machine : seed=42 ne suffit pas a reproduire exactement.
CloudEntrainement facture a l'heure de noeud (minimum ~1 h), endpoint facture tant qu'il est deploye. Ne rien lancer sans credits.
